# 阶段 3：技术方案落地

把已经选定的方案落到仓库里。目标是：**最小侵入、每步可运行、风格与仓库一致**。

没有方案就不要开写。缺 `选定方案`、`问题边界`、`成功标准`、文件清单或实现步骤时，先回到阶段 2。

## 输入

| 字段 | 说明 |
|------|------|
| `REPO_URL` | GitHub 地址，可用来对照远程约定 |
| `LOCAL_PATH` | 本地仓库根目录；缺省则用当前工作区 |
| 选定方案 | 名称 + 核心思路 |
| 问题边界 | 要解决的 + 明确不在范围内的 |
| 成功标准 | 怎样算做对 |
| 需要新增的文件 | 路径 + 职责 |
| 需要修改的文件 | 路径 + 改什么 |
| 实现步骤 | 有序列表 |

工作目录切到 `LOCAL_PATH`。不要在别的仓库里改。本阶段默认不 `git commit`。

## 工作流

```
- [ ] 0. 实现前准备（只读 + 跑通现有基线）
- [ ] 1. 只定义接口，然后停下来等用户确认
- [ ] 2. 按步骤实现核心逻辑（每步后仓库仍可运行）
- [ ] 3. 接入现有调用链
- [ ] 4. 按成功标准验证（demo + 单测）
- [ ] 5. 输出改动摘要和 Git 提交计划（默认不提交）
```

Step 1 结束后必须停。用户说「接口没问题 / 继续 / 进入 Step 2」之后才能写函数体。用户明确说「一次做完、不必停」时，才把 1~4 连着做，但仍先完成准备阶段。

---

## 0. 实现前准备

写任何代码之前做完这三件事。禁止边读边写。

1. **阅读所有需要修改的文件**，理解当前实现。
2. **检查项目的代码风格规范：**
   - 有无 `.eslintrc` / `pyproject.toml` / `ruff.toml` 等配置文件？
   - 现有代码使用的命名风格（snake_case / camelCase）？
   - 注释和 docstring 的书写习惯？
   - 类型标注的完整程度？
3. **确认当前主分支可以正常运行**（跑通 README 中的 quickstart 或现有测试）。

确认以上三点后，再开始实现。

准备完成后用几行说明：读了哪些文件、风格结论、基线命令和结果。然后才进入 Step 1。

---

## 实现原则

**逐步实现，每步可验证**
严格按照方案中的实现步骤顺序执行，每完成一步，项目必须仍处于可运行状态，不允许出现中间状态的残缺代码。

**最小侵入性**
- 优先扩展，而不是修改现有函数
- 若必须修改现有函数，只改必须改的部分
- 新增的公共接口保持向后兼容

**风格一致性**
新代码的命名、注释、类型标注风格必须与现有代码保持一致，不要引入项目中没有使用的新依赖，除非确实必要。

---

## Step 1：接口定义（先定义，后实现）

首先只定义新增的核心接口、类签名、函数签名，不写具体实现（函数体用 `pass` 或 `raise NotImplementedError`）。

完成后停下来，输出：

- 新增了哪些文件 / 接口
- 这些接口如何与现有代码衔接
- 有无发现方案设计时遗漏的依赖或冲突

确认接口设计合理后，再进入下一步。

---

## Step 2：核心逻辑实现

按照实现步骤依次完成每个文件的具体逻辑。

每个文件完成后输出：

- 文件路径
- 实现了什么
- 与方案设计有无偏差，若有，说明原因

此时仍不要把新模块接到主路径上，除非某文件本身就是那个接入点，且方案步骤已经排到它。

---

## Step 3：集成到现有代码

将新模块接入现有的调用链。

重点检查：

- 原有的调用方式是否仍然有效（不破坏现有用法）
- 新功能的触发路径是否完整
- 有无遗漏的错误处理分支

---

## Step 4：验证

按照方案中的验证策略逐项执行：

**手动验证：**
给出一个最小可运行的 demo 脚本，直接在终端可以跑通，证明核心功能有效。

**单元测试：**
为以下场景各写一个测试用例：

- 正常路径（happy path）
- 边界情况（如空输入、超长输入、工具调用失败）
- 与现有功能的兼容性（原有用法不受影响）

测试文件放在项目现有的测试目录下，命名风格与现有测试文件一致。

没跑通的不要写「已完成」。贴命令和实际输出摘要。失败就修，不要把红测试留给用户。

---

## 交付物

实现完成后，输出以下内容：

### 改动摘要

| 文件 | 操作 | 改动说明 |
|---|---|---|
| | 新增 / 修改 / 删除 | |

### Git 提交计划

按逻辑拆分为 2~4 个 commit，每个 commit 只做一件事：

```
commit 1: {type}({scope}): {描述}
改动文件：
改动原因：

commit 2: ...
```

`type` 只用：`feat` / `fix` / `refactor` / `test` / `docs`。只出计划，不要真的 commit，除非用户进入阶段 4。

---

## 实现过程中的注意事项

遇到以下情况时，停下来告诉用户，不要自行决定：

- 发现方案设计有遗漏，需要改动超出预定范围的文件
- 发现与现有代码存在冲突，无法在不破坏兼容性的前提下实现
- 有两种实现方式，各有利弊，需要人工决策
- 需要引入新的第三方依赖

遇到以下情况时，自行处理，但实现后说明：

- 方案中的伪代码需要调整以适配实际代码结构
- 需要补充方案中未提及的错误处理逻辑
- 测试用例的具体写法与方案描述略有不同

停下来时说明：冲突点、可选方案（各 1~2 句利弊）、你建议选哪个、需要用户拍板什么。

## 落盘

本阶段结束（或在接口确认门闩停下）时，把当前阶段产物写入 `ARTIFACT_ROOT`（默认 `<当前任务工作目录>/artifacts`）：

```
<ARTIFACT_ROOT>/project/<owner>-<repo>/implementation.md
```

至少包含：

- 当前进度（停在 Step 1 / 已完成 0–5）
- 改动摘要表
- Git 提交计划
- 验证结果（已跑的命令与是否通过；尚未验证则写「未跑」）

项目目录不存在则创建；已有则覆盖。接口门闩停下时也要落盘（便于续跑）。回复里可附上落盘路径。

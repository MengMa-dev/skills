# 阶段 2：生成 PR 技术方案

把阶段 1 的某一条方向收成可落地的方案。输出必须能直接作为阶段 3 的前置信息粘贴，不要写空泛架构文。

没有选定方向就不要做本阶段：用户必须指出 Top 3 的第 N 名，或等价地给出「要做的事 + 入口文件」。

## 输入

- `REPO_URL` / `LOCAL_PATH`
- 选定的 PR 方向（来自 Top 3 或用户指定）
- 阶段 1 里这条方向的入口文件、风险点、预估工作量

## 准备

写方案前先精读入口文件及其调用链、现有测试目录、`CONTRIBUTING.md`（若有）。文件路径必须是仓库里真实存在的路径，禁止编造模块名。

对照阶段 1 的预估工作量：方案完成后仍应落在「小 / 中 / 大」对应周期内。超出就缩小问题边界，而不是默默加大范围。

## 输出格式（字段名不要改）

**选定方案：**{方案名称及核心思路}

**问题边界：**{要解决的问题 + 不在范围内的问题}

**成功标准：**{判断方案有效的标准}

**需要新增的文件：**{文件路径 + 职责}

**需要修改的文件：**{文件路径 + 修改内容}

**实现步骤：**{有序步骤列表}

另外补上阶段 3 验证要用的一节（放在实现步骤之后）：

**验证策略：**

- 手动验证：最小可运行命令/demo
- 单元测试：happy path、边界（空输入/超长/非法输入/依赖失败等按方案选择）、原有用法兼容

## 写法要求

- 核心思路用 3~6 句说清：改哪一层、为什么比直接打补丁更好、怎样保持向后兼容。
- 问题边界必须同时写「做」和「不做」。不做的典型项：无关重构、换依赖、改公共 API 形状（除非这就是本 PR）。
- 成功标准必须可检查（命令、断言、行为），不要写「代码更清晰」。
- 实现步骤按「每步结束后仓库仍可运行」来拆，对应阶段 3 的逐步实现。
- 若存在两种合理接法，不要擅自定案：列出利弊并停下问用户。

## 落盘

在回复用户的同时，把本阶段完整方案写入 `ARTIFACT_ROOT`（默认 `<当前任务工作目录>/artifacts`）：

```
<ARTIFACT_ROOT>/project/<owner>-<repo>/design.md
```

- 项目目录不存在则创建；已有 `design.md` 则覆盖。
- 内容与聊天输出一致（含选定方案、问题边界、成功标准、文件清单、实现步骤、验证策略）。

输出结束后停，等用户确认方案再进入阶段 3。回复里可附上落盘路径。
